# VTX Binary Format Proposal

## Executive Summary

Replace CSV-based IMU data storage with a custom `.vtx` binary format to achieve:
- **~60-70% file size reduction** compared to CSV
- **Faster parsing** (no ASCII conversion overhead)
- **Extendible metadata** for device info, calibration, session notes
- **Random access** to any data point without full file scan
- **Future-proof** design with versioning and reserved fields

---

## Current CSV Format Issues

### Storage Inefficiency
```csv
timestamp_ms,accel_x,accel_y,accel_z,gyro_x,gyro_y,gyro_z,mag_x,mag_y,mag_z,quat_w,quat_x,quat_y,quat_z
1730000000123,0.12,-0.45,9.81,0.01,0.02,-0.01,45.2,12.3,-8.9,0.707,0.000,0.000,0.707
```

**Problems:**
- Each number stored as ASCII text (~10-15 chars per value)
- Comma delimiters add overhead
- Header row repeated information
- ~120-150 bytes per record
- No built-in metadata (device name, calibration, session info)
- Text parsing overhead on every read

### Example Size Calculation
**10-minute recording at 10Hz:**
- Records: 10 * 60 * 10 = 6,000 samples
- CSV size: ~720 KB - 900 KB
- VTX size: ~336 KB - 420 KB
- **Savings: ~58% reduction**

## VTX Binary Format Specification

### Version 1.0 Structure

```
┌─────────────────────────────────────┐
│        FILE HEADER (64 bytes)       │
├─────────────────────────────────────┤
│     METADATA (variable length)      │
├─────────────────────────────────────┤
│   DATA RECORDS (56 bytes each)      │
│              ...                     │
│              ...                     │
├─────────────────────────────────────┤
│      FOOTER (optional, 32 bytes)    │
└─────────────────────────────────────┘
```

---

## 1. File Header (64 bytes)

Fixed-size header for fast file validation and metadata.

| Offset | Size | Type     | Field             | Description                           |
|--------|------|----------|-------------------|---------------------------------------|
| 0      | 4    | char[4]  | magic             | "VTX\0" - File signature              |
| 4      | 2    | uint16   | version_major     | Format major version (1)              |
| 6      | 2    | uint16   | version_minor     | Format minor version (0)              |
| 8      | 4    | uint32   | metadata_length   | Size of metadata section in bytes     |
| 12     | 4    | uint32   | data_offset       | Byte offset where data records start  |
| 16     | 8    | uint64   | record_count      | Total number of data records          |
| 24     | 4    | float32  | sample_rate       | Recording frequency in Hz             |
| 28     | 8    | int64    | start_timestamp   | Unix timestamp (ms) of first sample   |
| 36     | 8    | int64    | end_timestamp     | Unix timestamp (ms) of last sample    |
| 44     | 1    | uint8    | record_format     | Bitmask for enabled fields (see below)|
| 45     | 1    | uint8    | compression       | Compression type (0=none, 1=zstd)     |
| 46     | 2    | uint16   | reserved1         | Reserved for future use               |
| 48     | 16   | byte[16] | reserved2         | Reserved for future use               |

**Record Format Bitmask:**
```
Bit 0: Has acceleration data (always 1 in v1.0)
Bit 1: Has gyroscope data (always 1 in v1.0)
Bit 2: Has magnetometer data
Bit 3: Has quaternion data
Bit 4-7: Reserved for future sensors
```

## 2. Metadata Section (Variable Length)

JSON-encoded metadata for flexibility and human readability during debugging.

### Schema
```json
{
  "device": {
    "id": "ABC123DEF456",
    "name": "Vertex IMU #1",
    "firmware_version": "1.2.3",
    "hardware_revision": "v1.0"
  },
  "session": {
    "created_at": "2025-10-28T14:30:00Z",
    "created_by": "user@example.com",
    "bike": "Bike 1",
    "position": "Seatpost",
    "notes": "Trail ride - rocky terrain",
    "tags": ["trail", "rocky", "test"]
  },
  "calibration": {
    "zero_point": {
      "roll": 0.0,
      "pitch": 0.0,
      "yaw": 0.0,
      "accel_x": 0.0,
      "accel_y": 0.0,
      "accel_z": 0.0,
      "gyro_x": 0.0,
      "gyro_y": 0.0,
      "gyro_z": 0.0,
      "mag_x": 0.0,
      "mag_y": 0.0,
      "mag_z": 0.0
    },
    "applied": true
  },
  "custom": {
    // User-defined fields for future extensions
  }
}
```

**Metadata is optional** - if `metadata_length = 0`, section is empty.

**Design rationale:**
- JSON for flexibility and debuggability
- Easy to extend without breaking format
- Minimal parsing overhead (only read once)
- Can be compressed in future versions

## 3. Data Records (56 bytes each)

Fixed-size binary records for efficient storage and random access.

### Full Record (56 bytes)
With all sensors enabled (accel + gyro + mag + quat):

| Offset | Size | Type    | Field         | Description                          |
|--------|------|---------|---------------|--------------------------------------|
| 0      | 4    | uint32  | timestamp_ms  | Milliseconds offset from start_time  |
| 4      | 4    | float32 | accel_x       | Acceleration X (m/s²)                |
| 8      | 4    | float32 | accel_y       | Acceleration Y (m/s²)                |
| 12     | 4    | float32 | accel_z       | Acceleration Z (m/s²)                |
| 16     | 4    | float32 | gyro_x        | Gyroscope X (rad/s)                  |
| 20     | 4    | float32 | gyro_y        | Gyroscope Y (rad/s)                  |
| 24     | 4    | float32 | gyro_z        | Gyroscope Z (rad/s)                  |
| 28     | 4    | float32 | mag_x         | Magnetometer X (µT)                  |
| 32     | 4    | float32 | mag_y         | Magnetometer Y (µT)                  |
| 36     | 4    | float32 | mag_z         | Magnetometer Z (µT)                  |
| 40     | 4    | float32 | quat_w        | Quaternion W                         |
| 44     | 4    | float32 | quat_x        | Quaternion X                         |
| 48     | 4    | float32 | quat_y        | Quaternion Y                         |
| 52     | 4    | float32 | quat_z        | Quaternion Z                         |

### Minimal Record (28 bytes)
With only accel + gyro (mag/quat omitted):

| Offset | Size | Type    | Field         | Description                          |
|--------|------|---------|---------------|--------------------------------------|
| 0      | 4    | uint32  | timestamp_ms  | Milliseconds offset from start_time  |
| 4      | 4    | float32 | accel_x       | Acceleration X (m/s²)                |
| 8      | 4    | float32 | accel_y       | Acceleration Y (m/s²)                |
| 12     | 4    | float32 | accel_z       | Acceleration Z (m/s²)                |
| 16     | 4    | float32 | gyro_x        | Gyroscope X (rad/s)                  |
| 20     | 4    | float32 | gyro_y        | Gyroscope Y (rad/s)                  |
| 24     | 4    | float32 | gyro_z        | Gyroscope Z (rad/s)                  |

**Notes:**
- Use `record_format` bitmask in header to determine record size
- Empty fields (when sensor not present) are omitted entirely
- Timestamp stored as offset saves 4 bytes per record
- IEEE 754 float32 provides sufficient precision for sensor data

---

## 4. Footer (Optional, 32 bytes)

Optional footer for data integrity and indexing.

| Offset | Size | Type     | Field       | Description                        |
|--------|------|----------|-------------|------------------------------------|
| 0      | 4    | uint32   | crc32       | CRC32 checksum of entire file      |
| 4      | 8    | uint64   | file_size   | Total file size for validation     |
| 12     | 20   | byte[20] | sha1_hash   | SHA1 hash of data section          |

**Footer is optional** - presence indicated by file size matching expected size + 32 bytes.

## Size Comparison

### 10-minute recording @ 10Hz (6,000 samples)

**CSV Format:**
```
Header:    ~110 bytes (column names)
Per row:   ~130 bytes (ASCII numbers + commas)
Total:     ~780 KB
```

**VTX Format (Full):**
```
Header:      64 bytes
Metadata:    ~500 bytes (typical)
Records:     336,000 bytes (6,000 × 56)
Footer:      32 bytes
Total:       ~336 KB (57% smaller)
```

**VTX Format (Minimal - no mag/quat):**
```
Header:      64 bytes
Metadata:    ~500 bytes
Records:     168,000 bytes (6,000 × 28)
Footer:      32 bytes
Total:       ~168 KB (78% smaller)
```

### 1-hour recording @ 10Hz (36,000 samples)

| Format       | Size    | Reduction |
|--------------|---------|-----------|
| CSV          | ~4.7 MB | baseline  |
| VTX (full)   | ~2.0 MB | 57%       |
| VTX (minimal)| ~1.0 MB | 79%       |

## Implementation Plan

### Phase 1: Core Format Implementation

**Android App (React Native + TypeScript):**
```typescript
// 1. Encoder (write VTX files)
interface VTXEncoder {
  createFile(metadata: VTXMetadata): Promise<VTXFile>;
  appendRecord(record: IMURecord): Promise<void>;
  finalize(): Promise<string>; // Returns file path
}

// 2. Parser (read VTX files)
interface VTXParser {
  open(filePath: string): Promise<VTXFile>;
  readHeader(): VTXHeader;
  readMetadata(): VTXMetadata;
  readRecord(index: number): IMURecord;
  readRecords(start: number, count: number): IMURecord[];
  close(): void;
}

// 3. Type definitions
interface VTXHeader {
  magic: string;
  version: { major: number; minor: number };
  metadataLength: number;
  dataOffset: number;
  recordCount: number;
  sampleRate: number;
  startTimestamp: number;
  endTimestamp: number;
  recordFormat: number;
  compression: number;
}

interface VTXMetadata {
  device?: {
    id: string;
    name: string;
    firmwareVersion?: string;
    hardwareRevision?: string;
  };
  session?: {
    createdAt: string;
    createdBy?: string;
    bike?: string;
    position?: string;
    notes?: string;
    tags?: string[];
  };
  calibration?: {
    zeroPoint?: IMUReading;
    applied: boolean;
  };
  custom?: Record<string, any>;
}

interface IMURecord {
  timestamp: number;
  accelX: number;
  accelY: number;
  accelZ: number;
  gyroX: number;
  gyroY: number;
  gyroZ: number;
  magX?: number;
  magY?: number;
  magZ?: number;
  quatW?: number;
  quatX?: number;
  quatY?: number;
  quatZ?: number;
}
```

**Implementation Details:**
- Use `react-native-fs` for file I/O
- Use `DataView` for binary read/write operations
- Implement streaming encoder to avoid memory issues
- Add buffering for efficient disk writes

### Phase 2: Web App Parser (Read-Only)

**Next.js TypeScript:**
```typescript
// Web-based VTX parser for analysis
class VTXWebParser {
  constructor(file: File);

  async parse(): Promise<VTXData>;
  async getHeader(): Promise<VTXHeader>;
  async getMetadata(): Promise<VTXMetadata>;
  async getRecords(start?: number, count?: number): Promise<IMURecord[]>;
  async export(): {
    toCSV(): Blob;
    toJSON(): Blob;
    toArray(): IMURecord[];
  };
}
```

**Features:**
- Parse VTX files uploaded by users
- Visualize IMU data in 3D
- Export to CSV for compatibility
- Display metadata in UI

### Phase 3: Migration Tools

**Bidirectional Conversion:**
```bash
# Convert existing CSV files to VTX
vtx-convert csv-to-vtx input.csv output.vtx

# Convert VTX back to CSV (for compatibility)
vtx-convert vtx-to-csv input.vtx output.csv

# Batch conversion
vtx-convert batch *.csv --output-dir ./vtx/
```

**Migration Strategy:**
1. Implement VTX encoder in Android app
2. Keep CSV export capability for 2-3 releases
3. Add "Convert to VTX" option in Data screen
4. Deprecate CSV in favor of VTX
5. Remove CSV support after user adoption

## Benefits

### Storage Efficiency
- **57-78% smaller files** depending on sensor configuration
- Reduced cloud storage costs
- Faster upload/download times
- More recordings fit on device

### Performance
- **Binary parsing is 5-10x faster** than CSV text parsing
- Random access to any sample without full file scan
- Efficient seeking for data visualization
- Lower memory usage during parsing

### Extensibility
- Metadata section for device info, calibration, session notes
- Version field for backward compatibility
- Reserved fields for future features
- Bitmask allows adding new sensor types

### Data Integrity
- Optional checksums for corruption detection
- File format validation via magic bytes
- Structured format prevents malformed data

### Professional Format
- Custom binary format signals serious engineering
- Better integration with analysis tools
- Industry-standard approach for sensor data

## Technical References

### Binary Format Best Practices
- Use little-endian byte order (standard for modern processors)
- Align fields to natural boundaries where possible
- Use IEEE 754 float32 for floating-point data
- Include version number for format evolution

### Related Formats
- **HDF5**: Hierarchical Data Format (too complex for our needs)
- **Apache Parquet**: Columnar format (overkill for time-series)
- **Protocol Buffers**: Good for serialization, but text-based metadata less flexible
- **Custom binary**: Best fit for our specific requirements
