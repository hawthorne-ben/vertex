# VTX Format v1.2 — Clock Sync Stream

**Status:** implemented
**Supersedes:** nothing. Purely additive to v1.1.
**Header size:** unchanged (64 bytes)

---

## 1. Motivation

Sample timestamps in a `.vtx` file are `uint32` milliseconds offset from the
start of the recording, derived from the ESP32's `millis()`. `millis()` is
driven by a crystal with a tolerance on the order of tens of ppm. Over a
multi-hour recording that is a measurable, monotonic divergence from a
NTP-backed phone clock — at 30 ppm, ~108 ms/hour.

Before v1.2 that divergence was invisible: the wall clock was sampled exactly
once (BLE `CMD_SYNC_CLOCK` at connect) and `start_timestamp` was assumed to
hold for the whole file. Any external timeline aligned against the file — a FIT
file from a head unit, video with burnt-in timecode — accumulates that error
silently.

v1.2 records the disagreement as data. It does **not** correct it. The device
time base is left untouched; correction is an offline decision made by a
consumer that can see the whole recording at once.

---

## 2. Design constraints

These are properties of the system, not preferences:

1. **`millis()` remains the sole time base for IMU samples.** Sync records are
   observations *about* the time base, never inputs to it.
2. **No in-situ correction.** Applying an offset mid-recording can make sample
   timestamps step backwards. The cloud DSP computes windowed RMS over the
   timestamp axis and assumes monotonicity; a backwards step produces a wrong
   answer rather than an error.
3. **Additive only.** Every `.vtx` file written before v1.2 must parse
   unchanged, and a v1.2 file must parse correctly in any reader that ignores
   the sync stream.
4. **A missed sync is normal, not an error.** BLE is usually disconnected
   during a ride. Zero sync records is a valid, expected file.

---

## 3. Header extension

The 64-byte header is unchanged in size. v1.2 claims the last 6 reserved bytes:

| Offset | Size | Type   | Field             | Notes                                  |
|--------|------|--------|-------------------|----------------------------------------|
| 58     | 4    | uint32 | sync_data_offset  | Byte offset of the sync section; 0 = absent |
| 60     | 2    | uint16 | sync_record_count | Number of sync records; 0 = absent     |

Full reserved-region history:

| Offset | Size | Claimed by | Field             |
|--------|------|------------|-------------------|
| 46     | 8    | v1.1       | gps_record_count  |
| 54     | 4    | v1.1       | gps_data_offset   |
| 58     | 4    | **v1.2**   | sync_data_offset  |
| 60     | 2    | **v1.2**   | sync_record_count |

**The reserved region is now fully consumed.** A future stream cannot be added
this way; it will require either a `uint16` section-table offset repurposed
from an existing field, or a v2.0 header. This is noted here because it is the
main cost of the chosen design.

`sync_record_count` is `uint16`, not `uint64` as GPS used. At the 60 s cadence
the ceiling of 65535 records is 45 days of continuous recording — far beyond
the battery envelope (single-digit hours). uint64 would not have fit in the
remaining space, and would have been 8 bytes to express a number that cannot
exceed ~1440 in practice.

### Version gating

A reader must key on `version_minor`:

- `version_minor >= 1` → GPS fields at 46 are meaningful
- `version_minor >= 2` → sync fields at 58 are meaningful

Readers must **not** infer presence from a non-zero value alone at an
unrecognized version. In practice all 42 pre-v1.2 sample recordings carry
zeros across bytes 46–63, so a value-based check happens to be safe today —
but that is an accident of the encoder zero-filling reserved space, not a
guarantee of the format.

## 4. Sync record layout (24 bytes, fixed)

| Offset | Size | Type   | Field              | Description                                   |
|--------|------|--------|--------------------|-----------------------------------------------|
| 0      | 4    | uint32 | t1_device_ms       | `millis()` when the device sent the request   |
| 4      | 4    | uint32 | t4_device_ms       | `millis()` when the device received the reply |
| 8      | 8    | int64  | t2_phone_unix_ms   | Phone `Date.now()` at receipt of the request  |
| 16     | 8    | int64  | t3_phone_unix_ms   | Phone `Date.now()` at send of the reply       |

Device timestamps are raw `millis()`, **not** offsets from recording start.
This is deliberate: a sync record's whole purpose is to characterize the
`millis()` time base itself, so it references that base directly and needs no
correction to be interpretable. Converting an IMU sample offset into the same
frame is `sample.timestamp_ms + recording_start_millis`, where the latter is
recoverable from the first sync record's own device clock, or supplied by the
caller.

Records appear in ascending `t1_device_ms` order.

### Why four timestamps

This is the NTP/SNTP clock-filter algorithm reduced to a single exchange. With
all four:

```
offset = ((t2 - t1) + (t3 - t4)) / 2
rtt    = (t4 - t1) - (t3 - t2)
```

`offset` is the phone-minus-device clock difference with the transport delay
cancelled to first order, and `rtt` is the round trip with the phone's own
processing time removed. The cancellation is exact only if the outbound and
return paths are symmetric; BLE is not reliably symmetric, so residual error
is bounded by roughly `rtt/2` and `rtt` becomes the per-sample quality weight.

Recording only `t1`/`t4` and a single phone time would fold an unknown, highly
variable BLE latency directly into the offset. At a connection interval of
30–50 ms, latency varies by tens of ms between samples — the same order as
several hours of accumulated crystal drift. Without RTT there is no way to
tell a bad sample from real drift after the fact.

Two extra `int64`s per record cost 16 bytes. At the 60 s cadence a 4-hour ride
holds 240 sync records = 5,760 bytes, against roughly 42 MB of IMU data. The
storage argument for a narrower record does not exist.

## 5. File layout

```
┌──────────────────────────────────────┐
│       FILE HEADER  (64 bytes)        │
├──────────────────────────────────────┤
│   METADATA  (variable, JSON)         │
├──────────────────────────────────────┤
│   IMU RECORDS  (28 or 56 bytes ea)   │   ← data_offset
├──────────────────────────────────────┤
│   GPS RECORDS  (44 bytes ea)         │   ← gps_data_offset, if any
├──────────────────────────────────────┤
│   SYNC RECORDS (24 bytes ea)         │   ← sync_data_offset, if any
└──────────────────────────────────────┘
```

### Trailing section vs. inline records — the tradeoff

**Chosen: trailing section.**

The decisive constraint is that the IMU region is a fixed-width array, and
both parsers exploit that to seek directly to sample *i*:

```
offset = data_offset + i * record_size
```

Interleaving a differently-sized record into that array destroys the
invariant. Every reader would have to scan linearly from `data_offset` to
find record *i*, or the format would need a discriminator byte per record —
28 bytes becomes 29 and every existing file is invalidated. Random access is
what the format was built for, and the web `vtx-samples` route and the
analysis scripts both depend on it.

Against that, trailing sections have real costs, and they are already visible
in the v1.1 GPS design:

- **The offset must be patched.** The device does not know where the sync
  section starts until recording ends, because it depends on the final IMU
  record count. The firmware writes sync records to a bounded in-RAM buffer
  and flushes them at `closeFile()`. A recording that loses power mid-ride
  keeps its IMU data (already on disk, header patched every ~10 s) but loses
  its sync records. Inline records would have survived. This is the sharpest
  argument against the chosen design, and it is accepted because a
  power-loss recording has bigger problems than drift correction.
- **Seeking is required.** Irrelevant here: the section is at most a few KB
  and readers already have the whole buffer.

An append-only sidecar file (`.vtx.sync`) was also considered and rejected:
the upload path, merge path, and storage layer all assume one file per
recording, and a second file would need its own lifecycle everywhere.

## 6. Backward and forward compatibility

**Reading old files with a new parser:** `version_minor < 2` → sync fields are
never read, `syncRecords` is `undefined`. Verified against all 42 `.vtx` files
in `analysis/data/sample-recordings/` (v1.0 and v1.1, formats 0x03/0x07/0x13/0x17).

**Reading new files with an old parser:** an unmodified v1.1 reader reads
bytes 58–63 as reserved and ignores them. It parses the header, metadata, and
all IMU records correctly; the sync section is past the end of the IMU array
and is never addressed. Record count and data offset are unaffected. No old
reader needs to change.

The one caveat is `recoveryMode` in the TS decoder, which infers record count
from `(fileLength - dataOffset) / recordSize` when the header is untrusted. A
trailing sync section inflates that estimate — 24 bytes per sync record read
as fractional IMU records. With the v1.2 header present the decoder now bounds
the scan at `sync_data_offset`; a genuinely corrupt header on a v1.2 file may
still over-count by up to `(24 * n_sync) / 28` records. This bug predates
v1.2 (GPS has the same interaction) and is bounded and documented rather than
fixed here, because recovery mode's premise is that the header is unreliable.

---

## 7. Interpretation (non-normative)

Sync records describe a linear relationship between the device time base and
true time. See `computeClockDrift()` in the TS and Python parsers for the
reference implementation; the fit method and its assumptions are documented
there and in `notes/clock-drift.md`.

A consumer that does not care about drift should ignore the section entirely.
That is the intended default.
